About This Project

Customer Account Takeover Detection — a supervised machine learning classification system built with Python and Flask.

Problem Statement

Account takeover (ATO) is a form of online fraud in which an attacker gains unauthorized access to a customer account, typically by using stolen credentials, credential stuffing, or phishing. Because the login is often performed with valid credentials, traditional password checks cannot detect it. The goal of this project is to build a machine learning classifier that flags login attempts that are likely to be account takeovers, based on behavioural and contextual features of the login attempt.

Objectives
  1. Load and clean a real-world login-attempt dataset.
  2. Engineer and preprocess features suitable for supervised classification.
  3. Train and compare three classification algorithms: Logistic Regression, Decision Tree and Random Forest.
  4. Evaluate each model using accuracy, precision, recall, F1-score, ROC-AUC and a confusion matrix.
  5. Select the best-performing model and save it with joblib.
  6. Deploy the model through a Flask web application with a user-friendly prediction form.
  7. Log all predictions and present them on a dashboard.
Dataset

Login Data Set for Risk-Based Authentication — a publicly available research dataset of large-scale single sign-on (SSO) login attempts. It is distributed through Zenodo (record 6782156) and provides a labeled Is Account Takeover field used as the target variable in this project.

The dataset contains the following features used by the model:

  • Round-Trip Time [ms] — server-side login latency
  • ASN — Autonomous System Number of the network
  • Login Successful — whether the login succeeded
  • Is Attack IP — whether the IP is in a known attacker list
  • Country, Region, City — IP-derived geography
  • Browser Name and Version, OS Name and Version, Device Type
  • Login Timestamp — used to derive login_hour and login_day_of_week

Note: the dataset is synthetic and is intended for research and educational use only. It should not be used to make real production decisions.

Machine Learning Methodology

1. Data loading & cleaning. The CSV is read with pandas. Identifier and free-text columns with very high cardinality (IP address, user agent string, user ID) are dropped because they would cause overfitting and inflate the feature space.

2. Feature engineering. The login timestamp is converted into two useful numeric signals: login_hour (0–23) and login_day_of_week (0–6).

3. Preprocessing pipeline. A scikit-learn ColumnTransformer applies: median imputation + standard scaling for numeric features, and constant imputation + one-hot encoding for categorical features. Rare categories are grouped with min_frequency=50 to keep the feature space manageable.

4. Train/test split. 80 % / 20 % stratified split, so the rare ATO class appears in both sets in the same proportion.

5. Model training. Three classifiers are trained with class_weight="balanced" to compensate for the severe class imbalance typical of fraud data: Logistic Regression, Decision Tree and Random Forest.

6. Evaluation. Accuracy, precision, recall, F1-score, ROC-AUC and a confusion matrix are computed on the held-out test set. Because the positive class is rare, F1-score is used as the primary selection criterion.

7. Deployment. The best pipeline (preprocessor + model) is saved with joblib and loaded by the Flask app at startup. The web form mirrors the trained feature schema, so new predictions use the exact same transformation pipeline.

Project Limitations
  • The dataset is synthetic and highly separable, so the reported metrics are optimistic. On real traffic, performance would be substantially lower.
  • The feature Is Attack IP is a strong indicator provided by the dataset, but in a live system it would not always be known at inference time.
  • Only a subset of the full dataset is used for training, to keep the project runnable on a student machine.
  • The model is not retrained automatically — it is a static snapshot saved to model.pkl.
  • Predictions are logged locally; there is no user authentication or role-based access control on the app.
Future Improvements
  • Add user-behaviour features (e.g. session history, typing cadence, geo-velocity).
  • Handle class imbalance with SMOTE or focal loss.
  • Compare with gradient boosting algorithms such as XGBoost or LightGBM.
  • Add threshold tuning to trade off precision vs. recall depending on business requirements.
  • Deploy with a proper database (SQLite or PostgreSQL) instead of a CSV log.
  • Add authentication and audit logging to the Flask app.
  • Set up automated retraining on new data.
